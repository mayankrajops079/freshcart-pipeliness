Teammate Question: After git commit, can your teammate see your code on GitHub? Why or why not?
Answer: No, your teammate cannot see the code. A commit is strictly a local operation stored within the local .git repository on your machine. It makes zero network calls. Teammates read from the remote repository hosted on GitHub. Until you run git push, the commits remain local and GitHub remains unchanged.

B2: Entity Traces

1. ORD-1003 Deduplication Trace

  • Bronze Ingestion: Arrives as two heterogeneous records:
    • Web (ingest_seq=3): {"order_id": "ORD-1003", "amount": "1200.00", "currency": "INR", "updated_at": "2026-09-03 14:00:00"}
    • Mobile (ingest_seq=7): {"orderId": "ORD-1003", "total": 1200.0, "curr": "INR", "lastUpdated": "2026-09-03 14:05:00"}
  • Deduplication (SQL_20_ORDERS_DEDUP): ROW_NUMBER() OVER (PARTITION BY order_id ORDER BY updated_at DESC, ingest_seq DESC) AS rn. The mobile record's updated_at (14:05:00) is newer than web (14:00:00). Mobile ranks rn = 1, Web ranks rn = 2. QUALIFY rn = 1 preserves the mobile version.
  • Gold Computation: amount_inr = 1200.00 * 1.0 = ₹1200.00. Customer Rohit M is Silver (multiplier 1). loyalty_points = FLOOR(1200 / 100) * 1 = 12 points.

2. ORD-1005 vs. ORD-1001 SCD2 Temporal Join

Customer Priya R (priya.r@gmail.com) has two periods in dim.customers_scd2:
Period 1: Silver (multiplier 1) from 2026-01-01 to 2026-09-04.
Period 2: Gold (multiplier 2) from 2026-09-05 to 9999-12-31.

Join Condition: LEFT JOIN dim.customers_scd2 c ON o.email = c.email AND o.order_date BETWEEN c.valid_from AND c.valid_to.

  • ORD-1001 (dated 2026-09-01): Falls in Period 1 (Silver, multiplier 1). Amount ₹500.00 -> 5 points.
  • ORD-1005 (dated 2026-09-10): Falls in Period 2 (Gold, multiplier 2). Amount $75.00 USD * 83.50 = ₹6262.50. Points = FLOOR(6262.50 / 100) * 2 = 62 * 2 = 124 points.

B5: Sixth Quality Check & Architectural Evaluation

Added check: "orders dated in the future": "SELECT COUNT_IF(order_date > CURRENT_DATE()) FROM silver.orders_dedup". Testing with future order ORD-9001 flagged 1 PROBLEM in both the future date check and the FX check, and was safely purged.

ETL vs. ELT Analysis: FreshCart illustrates ELT by preserving full raw JSON payloads in Bronze, enabling retroactive business rule updates (such as B3's currency validation) to reprocess complete history solely through scalable SQL compute without re-extracting from sources. Conversely, ETL performs transformations prior to loading, which is mandatory when handling sensitive PII (credit cards, tax IDs) that must never land in cloud storage in cleartext for regulatory compliance (GDPR/PCI-DSS). ELT leverages cloud data warehouse scalability, while ETL is optimal when target storage bandwidth or cost is prohibitive.

D3: Failure Modes & Protocol Semantics

  • Crash Before ACK: On a shared durable queue, unacknowledged messages are returned to the queue and redelivered with redelivered=True (at-least-once). On an exclusive queue (exclusive=True), the queue is deleted with the connection and unacknowledged messages are lost.
  • Poison Messages with requeue=True: A permanently invalid message is repeatedly returned to the front of the queue, causing an infinite failure loop that saturates CPU, floods logs, and blocks other messages (prefetch=1). Use requeue=False to discard or route to a Dead Letter Exchange.

Part E: Reflection

  1. What Broke: Future date test injected into Bronze caused quality check failures and duplicate counts during repeat runs.
  2. Diagnosis: Inspected Snowflake stage query history and confirmed COPY INTO appends each newly staged timestamped file.
  3. The Fix: Leveraged window deduplication in Silver and hash comparison in Gold MERGE to ensure complete downstream idempotency.
  4. Takeaway: Decoupling immutable raw storage from idempotent business transformations ensures resilient pipeline operations.
